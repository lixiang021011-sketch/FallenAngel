## 2. 一局的流转（口径与状态机）

**站点口径**：设计稿 §3.1 写的"演奏 7 / 商店 2 / 事件 3 / 休息 2 / 终房 1 = 16 个"相加是 15，
把**起点站**算进去才是 16。本文档与代码都按"起点 + 15 = 16"。

**状态机**（代码口径，`PortfolioGrowthRunData.phase`）：

```
MAP ──进入下一站──▶ READY（演奏类：普通演奏 / 硬仗 / 带关卡的终房）
 │                      │ 开始演奏
 │                      ▼
 │                   PLAYING ──打完──▶ RESULT ──继续──▶ MAP
 │
 └──进入下一站──▶ ROOM（商店 / 事件 / 休息 / 空占位 / 不带关卡的终房）
                      │ 离开
                      ├─ 普通房间 ──▶ MAP
                      └─ 终房 ─────▶ FINISHED（结算这一程）
```

四条边界规则（都是这一轮定下来的，写在这里免得以后当"本来就有的"）：

1. **只能往前走**：进入的房间必须是当前站的直接后继；走过的房间不能再进（`visitedNodeIds`）。
2. **打完最后一场不自动结束**：停在结算，玩家继续后回到地图，还要走进终房。
3. **终房的"离开"就是这一程的结束**：`Finish(CLEARED)` 在这里触发，此前不会结算局外积分。
4. **不走地图的旧路径**（`useMap = false`，自检与调试用）在最后一场后直接结算，没有房间可走。

## 3. 六类房间规格

每节六块：玩家看到的 → 机制 → 落点 → 验收 → 边界 → 依赖与待拍板。标 ❌ 的表示**还没有案**，
是本文档要补的部分。

### 3.1 起点站（Start）

- **玩家看到的**：地图最下面那一站，出发的地方（文案待写）。
- **机制**：不产生任何收支；只标定这一程的起点，记进 `visitedNodeIds`。
- **落点**：`PortfolioGrowthService.Begin`（现成）。
- **验收**：自检已在验（`Chapter starts at R00 with seven performances`）。
- **边界**：起点不接受"进入"（它是开局位置）；不能跳站到任何未相邻的房间。
- **依赖与待拍板**：无。

### 3.2 演奏房（Performance）

- **玩家看到的**：一个具体的地方——便利店门口、停车场、走廊、天桥下、天台、学校后门、
  没人的泳池边、商场中庭（设计稿 §3.2 的场景名）。**不显示"演奏房"这种系统词**。
- **机制**：进入即到 `READY`，点击开始这一曲；结算时按设计稿 §5.1 给奖励：
  三选一（左手器材）60% / 给钱 25% / 无事 15%；经验必有（`growth_score`）。
- **落点**：现成链路——`EnterRoom`（`STAGE`）→ `PortfolioSession.StartSong` → `CompleteSong` →
  `PortfolioIncomeService` / `RollStageDrop`。奖励比例常量在 `ChapterCatalog`。
- **验收**：自检已验（章程序列、现金、积分）；**掉落表要接新器材表**（等 §9 第 1 条）。
- **边界**：收益与掉落一律走结算服务，不在房间层算钱。
- **依赖与待拍板**：❌ **奖励三选一的界面与"三选一"本身还没做**（现在的奖励只有钱 + 掉落）。
  要做成"三件器材里挑一件"，先要商店/掉落接新表（§9 第 1 条）。

### 3.3 硬仗（HardFight）

- **玩家看到的**：**同一个地方，但人多、灯亮**（设计稿 §3.2）。
- **机制**：和演奏房同一条链，区别有三处——档位高一档、奖励保底至少一件蓝、掉落规则用
  `DP_CHALLENGE`、基础收益 150（普通 100）。现在"档位高一档"只在表里体现为关卡类型 `HARD`，
  **实际难度还没有分层**（曲库没有难度分层，见设计稿 §7 第 4 条与 roadmap D4）。
- **落点**：`PortfolioConfig.Stages` 的 `HARD` 行；`EnterRoom` 覆盖 `stageIds[completedSongs]`。
- **验收**：自检已验（硬仗选到 `S03`、收入 150）。
- **边界**：不额外改判定窗口（难度靠曲目与谱面，不靠暗改手感）。
- **依赖与待拍板**：❌ **入场路费怎么收**（§4）；❌ **"保底至少一件蓝"没实现**（掉落表只有概率，
  没有"保底稀有度"字段，需要给 `drop_rules` 加字段或给硬仗单开一条规则）；❌ 难度分档要等曲库。

### 3.4 商店（Shop）

- **玩家看到的**：旧货市场、音像店、小商品市场（设计稿 §3.2）。
- **机制**：进店生成候选（权重不放回、排除已持有）；**可以买，也可以卖**；刷新要花钱
  （设计稿 §6.2：首次 30，往后递增）。
- **落点**：现成——`DrawShopCandidates` / `ShopPanelController` / `PortfolioSession.AcquireEquipment`。
- **验收**：自检已验（进店出候选、报价、容量）。
- **边界**：卖出与置换要先定价格规则（§6.4），不能直接给个魔法数字。
- **依赖与待拍板**：❌ **卖的规则没有案**（§6.4）；❌ 刷新现在花的是"天赋发的刷新预算"，
  设计稿说的是花钱——两者并存还是换成花钱，待拍板；❌ 候选池要接新器材表（§9 第 1 条）。

### 3.5 事件房（Event）❌ 内容未定

- **玩家看到的**：一个"有人来过但没人"的地方（设计稿 §1.8 的空间清单）。
- **机制（设计稿一行）**：给 左手器材 / 右手纪念品 / 钱 / **置换** / **一段路**；
  要付"情境里的那个选择，好的那条总带代价"。旅伴也在这里遇到（设计稿 §3.6）。
- **落点（提案）**：新增 `EventCatalog`（事件表，见 §6.1）+ 一个事件面板；
  效果沿用现成口子——器材走 `AcquireEquipment`，钱走 `runCash`，负面走 `ModifierManager`（debuff），
  旅伴走将来的旅伴服务。**现在代码里事件房只有"过站"。**
- **验收（提案）**：每条事件一条自检（给什么/要什么与表一致）；能遇到旅伴的那几条要验"付人情才同行"。
- **边界**：事件不静默改数值——所有代价都写在表里（钱/器材/负面/人情），不许藏。
- **依赖与待拍板**：❌ 事件表（§6.1）；❌ 旅伴系统（设计稿 §3.6）与"人情"货币还没做；
  ❌ "置换"到底换什么（器材换器材？钱换路？）没有案。

### 3.6 休息房（Rest）❌ 内容未定

- **玩家看到的**：招待所、网吧包夜、候车厅的长椅（设计稿 §3.2）。
- **机制（设计稿一行）**：给 回状态 / 清一个负面 / 翻册子；要付"花掉一晚"——
  即**一晚只能选一件事**。
- **落点（提案）**：新增 `RestCatalog`（选项表，见 §6.2）+ 复用事件面板；
  清负面走 `ModifierManager.RemoveDebuffs()`（现成），翻册子走将来的册子系统。
- **验收（提案）**：自检——每层只有一个负面时"清一个负面"能清干净；选了一项就不能再选第二项。
- **边界**：休息房不产生收益、不接商店；"一晚一项"要在表里表达成 `pick = 1`。
- **依赖与待拍板**：❌ 负面状态系统（设计稿 §5.3：每层一个状态，四种）还没做——休息房的
  "清一个负面"和"回状态"都挂在它上面；❌ 册子系统没做。

### 3.7 终房（Final）

- **玩家看到的**：这一程的落点（设计稿 §2.2：你终于把那首曲子弹完的那一天）。
- **机制**：给 一件纪念品 + 结算 + 记进册子；离开即结束这一程。
- **落点**：`LeaveRoom` → `Finish(CLEARED)`（已落地）。纪念品与册子是内容。
- **验收**：自检已验（离开终房 → `CLEARED`，7/7 场，积分 900）。
- **边界**：终房不再带收尾演奏（设计稿把终房与 7 场分开计数）；结算只发生一次。
- **依赖与待拍板**：❌ 纪念品表与结算界面（§6.3）；❌ 设计稿 §7 第 9 条"那个人还在不在"的留白口径。

## 4. 硬仗的路费：三个方案（待拍板）

设计稿只有一句"档位高一档；**输了路费不退**"。但它没写路费**什么时候收**。直线地图上这件事
很要紧：如果进硬仗要现付、而玩家现金不够，就**卡死**（没有绕路可走）。三个方案：

| 方案 | 怎么收 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A 入场扣**（现有链路） | 进硬仗前扣现金，不够就进不去 | 与现有天赋 F0/F1、装备 E08（可选减免 20%）直接对接；报价界面已经在 | **会卡死**，必须再加一条兜底（允许欠账 / 免费进但奖励减半 / 最多欠一次） |
| **B 结算扣**（推荐） | 打完在结算里扣：赢了从收益扣、输了从补偿里扣，扣不出来就先欠着 | **不会卡死**；"输了路费不退"这句话最自然；报价从"进房前"挪到"结算后" | 现有 E08 的口径（"成功支付并进入才消耗"）要改；结算面板要多一行 |
| **C 恢复分叉** | 硬仗（收费）与普通演奏（免费）二选一 | 完全避开卡死；保留"要不要冒这个险"的张力 | 房间数从 16 变 17，设计稿的总数要改 |

我的建议是 **B**：它只改"何时扣钱"，不改"扣多少"，也不与任何天赋/装备的语义打架。
选它的话要顺带把 §6 的结算行与 E08 的文案一起定。

**未选之前，表里所有 `route_price` 保持 0**（现在的状态），收费链路原样留着。

## 7. 数值：7 场之后的现状与旋钮（模拟器实测 2026-09-27）

跑 `python balance/balance_sim.py`（已按章节地图更新）得到：

| 项 | 现在（7 场） | 设计稿 §6.1 的旧值（3 场） |
| --- | --- | --- |
| 一局收入 | **800 – 1048** | 320 – 338 |
| 每局积分 | **900**（800 演奏 + 100 通关） | 550 |
| 局末余现金 | **约 500 – 700** | 约 120 – 150 |
| 买到的器材 | 5.6 – 6.8 件（容量 20） | 3.8 – 5.0 件 |
| 天赋树 3600 分 | **约 4 局解锁完** | 6 – 8 局 |

三只旋钮，按优先级：

1. **局外成长节奏**：一局积分 550 → 900，天赋树总价 3600 就显得便宜了。要么提高总价、要么把
   `growth_score` 降下来、要么接受"4 局解锁完"（设计稿 §7.2 就是这条未定项）。
2. **容量 20 → 8**（设计稿 §5.2）：现在余现金 500–700 而容量 20，钱几乎花不完；
   改成 8 格之后"买哪件"才重新变成选择。
