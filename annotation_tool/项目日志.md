# Listening AI · 项目日志

> 为什么放在这里：Listening AI 这条线是 annotation tool 的副产品 —— 先有了这台标注工具，才长出"在自然听歌里采集 moment-level 人工反馈"这个研究问题。工具本体见本目录 `README.md`，安卓端见 `../annotation_android/`。

---

## 项目现状（2026-10-08 通读代码后整理）

**两个客户端，一套数据模型**

- `annotation_tool/` —— 手机浏览器版。自己拥有音频（master + 各分轨），用一条 song clock 同步播放，能在 review 里 solo 单轨、重放区间。
- `annotation_android/` —— 原生版。没有音频，读系统 MediaSession（歌名 / 艺人 / 时长 / 位置）来知道"现在在放什么"，配一个悬浮条，让你用平常的播放器听歌、在别的 app 上标注。
- 两者导出同一份 JSON schema，喂同一个研究数据库。

**数据语义（这套东西的底线，改动前先想清楚）**

- raw events 是唯一真相；region / interval 只是派生视图，永远不覆盖原始事件。
- 不吸附音符、不吸附节拍、不做反应时校正 —— 按下的一刻歌曲在哪，就记哪。
- 播放位置一变（seek / restart / 歌尾 / 退出），已打开的区间会在**跳转之前**自动关闭，带 `autoClosed` + `closeReason`。
- 重复听同一首歌是独立 session，不覆盖 —— 这是为"注意力是否可复现"这个问题留的。
- **没有标注 ≠ 负样本**，只记正向证据。

**本地优先**

- 先写本地（网页 localStorage / IndexedDB，安卓 SQLite），再进重试队列（指数退避、按 eventId 幂等）。断网、服务器挂了都不影响听歌。
- 音频从不上传，后端只看到歌曲元数据、session、raw events 和 review 备注。

**已经为"批量听"做的**

- 整库导入：一个文件算一首歌，跳过重复，存储满了会停下并告诉你导了多少。
- 库头部显示 N / M、已听多少、还没听多少；会话结束进 review，8 秒后自动开始下一首 —— 只要你碰了 review（选区间、写备注），倒计时就取消。
- 听歌界面有 **End → Next song**，判定这首歌不值得回看时直接跳过，session 照样留着。

**刻意没做**

chart、波形、STRUM 接入、节拍吸附、AI 分析、固定的标注分类体系、评分、推荐、dashboard、账号、音频上传管理。

**验证情况**

- 网页端 `npm test`：25 个测试（区间派生、seek/restart/歌尾的自动关闭、时间戳保真、schema、幂等上传、队列排空）。
- 安卓端 `.\build.ps1 -Task test`：40 个 JVM 单测；debug APK 可产出、可签名安装。
- **未验证**：真机上的 now-playing 捕获、悬浮条、对某个具体播放器的 seek 判定 —— 这台机器上没有设备也没有模拟器，装到手机上才算数。

## 2026-10-08｜文献不只用于"学方法"，还应直接进入研发流水线

今天重新梳理 Music AI / MIR / Active Learning / Human-in-the-loop / Music HCI 相关文献后，确认了一件此前没有充分重视的事：

项目不应该只从论文中学习概念和方法，还应该主动复用论文已经产出的模型、数据集、实验工具、baseline 和交互范式。

此前的思路更偏向：

```text
发现问题 → 自己设计模型/交互 → 实现 → 再找文献解释
```

现在调整为：

```text
明确研究问题 → 查找已有成果 → 复用可用 artifact → 只开发真正缺失的部分
```

这能明显减少重复造轮子，也让项目更容易进入已有研究语境。

### 当前可直接复用的成果

**预训练模型 / 表征**

- **OpenL3**
  可直接提取带时间信息的 audio embedding。适合先做连续音乐表征和 novelty curve，验证"embedding 变化大的位置是否更值得关注"。
- **musicnn**
  音乐专用 tagging / embedding 模型。可作为第一批 music representation baseline，输出乐器、风格、节奏等粗粒度语义及中间层 embedding。
- **Essentia pretrained models**
  可作为现成音乐模型库，优先检查其中已有的 ONNX / tagging / embedding / tempo / instrument 等模型，避免单独重复寻找和训练。
- **MERT**
  更强但更重的音乐 representation baseline。暂时主要用于 PC / 云端对照，不作为第一版移动端部署目标。

**数据集**

- **DEAM**
  包含 time-aligned dynamic emotion annotation。

  第一阶段可不招募用户，先做离线 sanity check：

  ```text
  连续 music embedding
  → novelty peaks
  vs
  人类连续情绪标注发生明显变化的位置
  ```

  它不能证明"interesting moment"，但可以初步判断现成 music representation 是否至少能感知人类可察觉的音乐变化。
- **TagATune 等 crowdsourced music annotation datasets**
  可用于了解大众音乐语义标签的粒度和分布，以及早期 human computation 如何把用户反馈变成机器学习数据。

**可直接复用的实验范式**

- **MuPsych / Music Experience Sampling**
  已有真实移动端、自然听歌环境中的音乐体验采集研究。

  需要重点借鉴：
  - 自然听歌场景中的 prompt 设计
  - 用户忽略 / Not now 机制
  - field study 的参与者依从性
  - self-selection bias
  - 技术限制
  - listening context 的记录方式

  项目不应该重新从零摸索一套自然听歌实验方法。
- **μEMA**
  证明极短、极低操作成本的 microinteraction 可以降低主观负担。

  这和当前"尽量不用长问卷、不要求文字输入、优先一两次点击"的方向一致。
- **JITA-EMA / interruptibility**
  未来用于设计：

  ```text
  什么时候应该问
  什么时候只提示
  什么时候应该保持沉默
  ```

  而不是简单使用固定 novelty threshold。

**可直接复用的算法 baseline**

Active Learning 已经有成熟策略，不需要自己发明：

- Random sampling
- Uncertainty sampling
- Entropy sampling
- Query-by-committee
- Disagreement-based selection

因此以后若研究"哪些 moment 值得向用户询问"，必须至少和其中若干已有 baseline 比较。

### 当前形成的研发原则

1. **先找 artifact，再决定是否自己做。**

   每出现一个新需求，先检查：
   - 是否已有公开模型
   - 是否已有公开 checkpoint
   - 是否已有数据集
   - 是否已有 experiment protocol
   - 是否已有标准 metric / baseline

2. **第一版研究不训练"大音乐理解模型"。**

   先验证：

   ```text
   现成 music representation
   → candidate moment detection
   → human feedback
   ```

   是否成立。

   如果现成表征已经足够，就把研究资源投入 query policy / interaction / personalization；只有明确不够时再训练模型。

3. **文献综述以后同步维护"研发资源地图"。**

   每篇重点论文至少记录：
   - Paper
   - Research question
   - 可复用模型
   - 可复用数据
   - 可复用代码
   - 可复用 protocol
   - 可复用 metric
   - 对当前项目的直接用途

   避免文献阅读与实际研发脱节。

### 最近可执行的最小实验

第一轮优先：

```text
OpenL3 / musicnn
→ 连续 embedding
→ novelty curve
→ candidate moments
→ 与 random moments 对照
```

同时用 DEAM 做离线 sanity check。

当前需要回答的不是"AI 能不能真正理解音乐"，而是：

> 现成音乐表征是否已经足以从连续音乐中找到更值得进一步观察的局部变化？

只有这个问题成立，才继续投入主动提问、机会式交互和个性化学习。

### 项目定位上的变化

项目逐渐从"做一个 AI 音乐伴侣"转向一个更具体的问题：

> 如何利用已有音乐表征和低成本人类反馈，在自然听歌过程中获取 time-aligned、可学习的 moment-level music data？

其中真正可能形成贡献的部分，不一定是新的底层 MIR 模型，而可能是：

- moment selection
- query policy
- low-burden elicitation
- mixed-initiative interaction
- personalized human feedback
- audit / correction pipeline

因此后续研发应优先把已有学术成果变成基础设施，而不是重复解决已经有成熟答案的问题。
